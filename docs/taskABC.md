# 后端开发任务分工

本文是三名后端开发人员的公共任务文档。A、B、C 同时开展后端开发；前端等待后端开发和验收完成后再启动。本文中的 A、B、C 仅指三名后端人员，与现有历史文档或代码注释中的负责人字母可能不同，分工以本文为准。

## 当前基础

- FastAPI、数据库会话、接口 DTO、路由和前端工程已搭建；多数业务接口仍为占位实现。
- 用户提供的 ORM 和初始迁移 `20261104_0001` 已接入。用户确认该迁移尚未执行，本项目尚未验证真实 MySQL 建表和业务流程。
- 数据模型以用户提供的 ORM 为基础；共享接口及数据库结构限制见 [公共接口契约](contracts.md) 和 [后端开发基线](backend-baseline.md)。用户要求暂不修改数据库结构。

## A：用户、草稿与数据库基础

**目标：实现认证和用户数据的保存，为其他模块提供可靠的草稿数据。**

### 任务

- [ ] 配置开发和测试 MySQL；确认目标库及现有数据后执行初始迁移，验证实际表结构与连接。
- [ ] 实现登录、退出、当前用户查询、密码安全存储和身份验证。
- [ ] 实现草稿创建、查询、修改，以及预算、日期、人数和偏好的保存。
- [ ] 实现住宿、餐饮和景点选择的添加、删除与持久化。
- [ ] 实现用户隔离、事务、草稿版本原子检查及添加选择的幂等。
- [ ] 牵头协调通用幂等方案；负责整合数据库公共配置和后续迁移，涉及共享模型的变更须与 B、C 评审。
- [ ] 编写自动化测试，并向 C 提供读取当前用户草稿的服务接口及错误约定。

### 负责接口

| 方法 | 路径 | 内容 |
| --- | --- | --- |
| POST | `/api/v1/auth/login` | 登录 |
| POST | `/api/v1/auth/logout` | 退出 |
| GET | `/api/v1/auth/me` | 当前用户 |
| POST | `/api/v1/drafts` | 创建草稿 |
| GET | `/api/v1/drafts/{draft_id}` | 查询草稿 |
| PATCH | `/api/v1/drafts/{draft_id}` | 修改草稿 |
| POST | `/api/v1/drafts/{draft_id}/selections` | 添加选择 |
| DELETE | `/api/v1/drafts/{draft_id}/selections/{selection_id}` | 删除选择 |

主要代码范围：`backend/app/auth/`、`backend/app/drafts/`、`backend/app/db/` 和相关公共配置。

### 验收

- 登录后可以创建、查询和修改自己的草稿，并添加、删除选择。
- 不同用户的数据不能互相访问；无效身份无法访问受保护接口。
- 并发修改能正确返回版本冲突，重复添加请求不会产生重复数据。
- 数据库迁移在测试 MySQL 上执行成功；核心功能及异常情况有自动化测试。

## B：外部数据、候选与智能助手

**目标：提供候选、地图、天气及模型能力，将用户输入转换为可校验的建议。**

### 任务

- [ ] 实现住宿、餐饮、景点候选搜索和详情，统一数据来源、价格和坐标等字段。
- [ ] 接入地图和路线服务，实现路线估算，处理失败、超时和服务不可用。
- [ ] 接入天气服务，提供指定地点和日期的天气数据。
- [ ] 实现模型供应商适配、超时、重试和结构化输出校验。
- [ ] 实现草稿助手的需求理解、补充提问和建议生成。
- [ ] 实现计划助手的查询或修改意图识别；助手输出作为建议，不能绕过用户确认直接修改数据。
- [ ] 编写使用外部服务替身的自动化测试，并提供真实服务联调记录。

### 负责接口

| 方法 | 路径 | 内容 |
| --- | --- | --- |
| GET | `/api/v1/catalog/search` | 候选搜索 |
| GET | `/api/v1/catalog/items/{item_ref}` | 候选详情 |
| POST | `/api/v1/routes/estimate` | 路线估算 |
| GET | `/api/v1/weather` | 天气查询 |
| POST | `/api/v1/drafts/{draft_id}/assistant/messages` | 草稿助手 |
| POST | `/api/v1/plans/{plan_id}/assistant/messages` | 计划助手 |

主要代码范围：`backend/app/catalog/`、`backend/app/integrations/` 和独立的助手服务文件。助手路由目前位于 `backend/app/planner/router.py`，由 C 统一管理该文件；B 提供助手服务并与 C 对接。

### 验收

- 候选、路线和天气接口能返回符合约定的数据，标明数据来源及适用条件。
- 外部服务超时、失败或不可用时返回明确错误，不把失败当成成功。
- 助手输出经过校验，用户确认前不直接写入业务数据。
- 外部服务替身测试通过，并记录可用凭据和环境下的真实服务联调结果。

## C：行程确认、规划与版本

**目标：根据用户确认的信息生成行程，并支持安全查询和修改。**

### 任务

- [ ] 实现输入确认：检查用户归属、草稿版本和选择，保存确认快照。
- [ ] 实现计划生成：使用确认快照、候选数据和模型建议，检查必选项、时间及预算。
- [ ] 实现计划列表、计划详情和行程项目查询。
- [ ] 实现规划任务状态查询、计划重命名和归档，并处理权限与并发。
- [ ] 实现修改预览、确认及历史版本保存，检查版本和预览有效期。
- [ ] 实现生成和修改确认的幂等、事务处理及失败恢复。
- [ ] 对接 A 的草稿服务和 B 的地图、天气及模型服务。
- [ ] 编写规划、并发、用户隔离和异常恢复的自动化测试。

### 负责接口

| 方法 | 路径 | 内容 |
| --- | --- | --- |
| POST | `/api/v1/drafts/{draft_id}/confirm` | 确认草稿输入 |
| POST | `/api/v1/plans` | 生成计划 |
| GET | `/api/v1/planning-requests/{planning_request_id}` | 查询规划任务 |
| GET | `/api/v1/plans` | 计划列表 |
| GET | `/api/v1/plans/{plan_id}` | 计划详情 |
| PATCH | `/api/v1/plans/{plan_id}` | 重命名 |
| DELETE | `/api/v1/plans/{plan_id}` | 归档 |
| GET | `/api/v1/plans/{plan_id}/items` | 查询行程项目 |
| POST | `/api/v1/plans/{plan_id}/revisions/preview` | 预览修改 |
| POST | `/api/v1/plans/{plan_id}/revisions/{preview_id}/confirm` | 确认修改 |

主要代码范围：`backend/app/planner/`。C 负责整合该目录中的路由；助手业务由 B 实现并对接。

### 验收

- 可以从确认快照生成计划，查询计划及项目，并预览、确认修改。
- 重复请求不会重复生成或应用修改；旧版本不能覆盖新版本。
- 失败不会破坏已有计划；用户隔离、预算、时间和版本冲突有自动化测试。
- 与 A、B 完成约定接口的联调，并保留历史版本。

## 共同约定与并行方式

1. **按共享契约并行实现。** API 的价格区间、活动类型、部分草稿及规划任务接口已有基线；转换和业务仍待实现，详见 [后端开发基线](backend-baseline.md)。
2. **统一幂等方案。** API 允许 8–128 字符的键，规划请求模型字段为 64 字符；添加选择、生成计划、确认修改均需要幂等。用户要求暂不修改数据库结构，A 牵头、C 参与研究并验证可靠方案；不得截断键或宣称尚未验证的重试行为已经实现。
3. **约定服务边界。** C 通过 A 提供的草稿服务读取用户数据，通过 B 的适配服务获取外部能力。先确定输入、输出和错误；其他模块未完成时，测试可使用替身，并在集成阶段替换验证。
4. **协调共享文件。** 共享 ORM、迁移、公共配置和接口契约变更由相关负责人共同评审；C 管理规划路由文件，B 提供助手服务。三人各自负责自己的测试。
5. **管理代码。** 当前项目目录尚未初始化 Git 仓库。建议建立共享仓库，每人使用独立分支，完成评审后合并。
6. **同步接口文档。** API 变更时更新后端 DTO 和 OpenAPI；前端启动前提供冻结版本和可用样例。凭据通过本地配置管理，不提交到仓库。

## 后端联调及前端启动条件

1. A、B、C 并行完成各自模块及测试。
2. 联调完整流程：登录 → 创建草稿 → 搜索并添加选择 → 确认 → 生成计划 → 查询 → 预览并确认修改。
3. 验证真实 MySQL 迁移、权限隔离、版本冲突、幂等，以及外部服务超时和异常处理；记录未通过项目。
4. 更新并冻结 OpenAPI，提供可运行的后端、测试结果和接口样例。
5. 以上后端工作和验收完成后，再启动前端开发。
