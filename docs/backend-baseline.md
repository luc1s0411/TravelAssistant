# 后端并行开发基线

更新日期：2026-11-04。分工以 [taskABC.md](taskABC.md) 为准，产品目标和验收用例见 [原始需求说明书](reference/需求说明书.md)。本文确定当前接口设计及未解决的限制；DTO、路由和测试不等于业务已经实现。

## 可用的工程基线

- Python 3.12、FastAPI、Pydantic、SQLAlchemy、Alembic、MySQL 8.4；后端依赖以 `backend/requirements.lock` 为准。
- 所有业务接口使用 `/api/v1`、`snake_case`、字符串 ID、统一响应和分页。`backend/app/*/schemas.py` 是 DTO 定义，`docs/openapi.json` 是生成快照。
- 数据库使用用户提供的 ORM、现有事务依赖及初始迁移 `20261104_0001`。用户要求暂不修改数据库结构；本轮未增加字段、表或迁移，也未连接实际 MySQL。
- 接口业务尚未实现；没有身份时返回 401，获得测试身份后未实现的业务返回 501。不能把占位接口当作真实成功。

## 模块衔接

- A 实现 `DraftService.get_owned(draft_id, user_id)`，返回当前用户可访问的草稿 DTO；无权访问与不存在统一返回 404。C 不接受客户端提供的用户 ID 作为权限依据。该服务当前仍是占位。
- B 提供候选、路线、天气及模型适配器，明确超时、来源和错误；C 只消费经过校验的结果。适配器不能把模拟数据标为真实来源，也不能向模型开放任意 SQL、代码或文件访问。
- C 负责确认快照、规划任务、计划和版本；B 实现助手服务，C 整合 `planner/router.py` 的助手路由。共同修改公共 DTO、配置或接口时先协调。
- API 使用 `dining`，数据库使用 `food`；API 坐标系 `GCJ02` 对应 ORM `gcj02`。`backend/app/db/mapping.py` 已提供分类、坐标类型与价格的纯转换函数；实际读写须在服务层调用，禁止不经转换把 API 枚举直接写入数据库。WGS84 不能只改标签当作 GCJ02。

## 数据与接口约定

### 草稿

`POST /drafts` 接受空 `trip` 或部分输入；保存的草稿可以逐步补齐目的地和日期。`PATCH /drafts/{id}` 提交当前完整 `trip` 对象和 `expected_revision`，不是深层合并；已有日期同时存在时结束日期不得早于开始日期。确认和生成前必须校验目的地、开始及结束日期、用户归属和当前版本；尚未补齐时返回明确的字段错误，不能生成成功计划。

到离时间是目的地本地时间，须结合对应日期与 `Asia/Shanghai` 转为有时区时间，数据库保存 UTC；恢复时按原时区转换。`preferences` 列表与 JSON 的具体字段约定应在 A、B 联调前确定，不能丢失内容。

### 价格与计划项目

- `price_min_minor` 和 `price_max_minor` 均以整数分表示，币种 CNY。未知价上下限均为 null；明确免费为 `0, 0`；单一报价上下限相等；区间的上限不得小于下限。参考价可只有下限，带条件报价及用户填写价格必须有上下限。
- 价格单位与 ORM 一致：`room_night`、`person_day`、`person_trip`、`person`、`item`、`vehicle`、`total`。如按人每餐或每次参观计价，须在 JSON `conditions` 明确说明具体口径，不能推测单位或将不同口径直接换算。
- 已知费用区间用 `known_subtotal_min_minor` 和 `known_subtotal_max_minor` 表示；无法计算上限时上限为 null。未知价项目须列入 `unknown_item_ids`，不能当零价。价格查询时间必须带时区。
- 计划项目支持住宿、餐饮、景点、休息和自由活动；休息和留空可以没有 `selection_id` 或价格。跨日活动须使用 `end_date` 明确结束日期。新的商家建议必须经过用户确认。

### 规划任务及计划管理

- `POST /plans` 未来接收确认编号及幂等键，返回 202 和 `PlanningRequestOut`，任务状态为 `pending`、`running`、`succeeded`、`failed`。
- `GET /planning-requests/{planning_request_id}` 仅能读取当前用户的任务。成功状态包含 `plan_id`；客户端按该 ID 获取计划。提交响应丢失时使用原请求和原幂等键重试，必须取得同一任务。
- `PATCH /plans/{plan_id}` 重命名，`DELETE /plans/{plan_id}` 从列表归档并保留历史；都须验证用户和 `expected_version`。行程版本号不单独提供元数据变更并发版本，重命名与归档的竞争策略仍需 C 实现前确定。
- 本节仅是接口契约，所有新路由当前返回 501。任务调度、提交事务、状态恢复、错误和计划持久化均待 C 实现。

## 优先阻塞项

1. **固定时间：** 当前 `trip_selections` 没有专门的固定开始时间字段。用户已明确暂不改数据库结构；实现前需确定并验证不丢失数据的持久化方案。不能返回“保存成功”却丢失时间，也不能依靠客户端内存充当已保存数据。
2. **完整幂等：** `planning_requests.idempotency_key` 最多 64 字符，可考虑存储包含操作范围的完整键的 SHA-256 摘要，`request_hash` 用于识别相同键不同输入；必须在数据库事务中处理并发。选择和修改确认没有通用的持久化幂等记录；现有结构能否可靠满足相同用户、操作、键、输入的完整重试语义尚未证明。不能截断键，也不能将进程内缓存当作可靠的持久化方案。
3. **认证和退出：** 需要选择密码哈希、凭证过期及退出后失效的实现；现有用户表没有单独的会话记录。不能因为表不存在就宣称退出已撤销凭证。
4. **实际环境：** 当前尚未验证 MySQL、初始迁移、供应商账号、配额及允许保存的数据；不得把离线 SQL 或替身测试当作真实通过。
5. **状态和恢复：** 需定义草稿及任务状态的可靠来源，以及任务运行中服务重启后的恢复、超时和重试策略。不能仅配置超时数字就视为已经实现。

在不改变数据库结构的前提下，这些问题可以继续设计和测试，但在方案与证据具备前不能标记为已解决，也不能据此宣称后端已可完整联调。

## 性能和验收

需求文档中的性能数值是待评审的建议：自有查询在 10 并发下 P95 不超过 1 秒、60 秒内每秒不少于 5 个简单读请求且错误率低于 1%；外部查询建议超时 15 秒，规划建议超时 120 秒、默认并发限制 3。应先记录硬件、数据量、并发、样本量与测试方法，再分别测试自有服务与真实供应商；不对第三方服务进行未经授权的压力测试。

完成业务后至少执行：MySQL 迁移及数据隔离测试、日期价格规则、并发版本冲突、幂等和故障恢复、外部服务异常、完整业务接口联调；结果按通过、失败、未验证或外部条件阻塞记录。后端完成并验收后再进行前端开发和手机、桌面端流程验收。
